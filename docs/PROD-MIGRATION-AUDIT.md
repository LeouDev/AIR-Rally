## Recommendation — reconsider the goal

The brief asks to migrate "the intended production data from staging." Based on the audit,
**that set is close to empty.**

Staging is a test environment: demo venues, test bookings with sandbox payment identifiers,
credits I minted for verification, and script leftovers. Promoting any of it would put
sandbox payment references and fabricated credit balances into production — the exact
outcomes Rules 5, 6, 8, 9 and 10 exist to prevent.

What production actually needs is **the schema**, not the data:

1. Apply migrations `029`–`046` in order.
2. Migrate **no** application rows.
3. Create the real venues in production through the normal owner-onboarding flow, so they get
   real owners, real approval, and real payment accounts.
4. Handle the one or two real users through Supabase's Admin API, or simply have them sign up
   again — with no production bookings yet, there is nothing to preserve.

This is faster, and it is the only version that leaves production's payment and credit state
truthful.
